3.2 New Database Tables (Admin-Specific)

-- Admin-specific tables to ADD to existing schema

-- Platform configuration (key-value store)
CREATE TABLE platform_config (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  key TEXT UNIQUE NOT NULL,
  value JSONB NOT NULL DEFAULT '{}',
  description TEXT,
  updated_by UUID REFERENCES profiles(id),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- Feature flags
CREATE TABLE feature_flags (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT UNIQUE NOT NULL,
  enabled BOOLEAN DEFAULT false,
  description TEXT,
  target_orgs UUID[] DEFAULT '{}',  -- empty = all orgs
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- Platform announcements
CREATE TABLE announcements (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  type TEXT CHECK (type IN ('info', 'warning', 'maintenance', 'feature')),
  active BOOLEAN DEFAULT true,
  starts_at TIMESTAMPTZ DEFAULT now(),
  ends_at TIMESTAMPTZ,
  created_by UUID REFERENCES profiles(id),
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Admin audit log
CREATE TABLE admin_audit_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  admin_id UUID REFERENCES profiles(id),
  action TEXT NOT NULL,
  target_type TEXT,  -- 'user', 'org', 'lead', 'config', etc.
  target_id UUID,
  details JSONB DEFAULT '{}',
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Profiles table: add is_super_admin column
ALTER TABLE profiles ADD COLUMN is_super_admin BOOLEAN DEFAULT false;

    admin/

      users/[id]/route.ts      ← GET user detail, PATCH update
      organizations/route.ts   ← GET all orgs with aggregates

4.2 Admin Auth Flow

User logs in via /login (standard Supabase Auth)
↓
Middleware checks session on /admin/* routes
↓
Server component queries profiles table: is_super_admin = true?
↓ Yes → Render admin page     ↓ No → Redirect to /app/dashboard
Admin API routes verify super-admin before every operation using service_role client

4.3 Settings Backend Data Flow

Admin UI: toggle feature flag / update config
↓
POST /api/admin/flags or PUT /api/admin/config
↓
API validates super-admin → writes to platform_config / feature_flags tables
↓
admin_audit_log entry created automatically
↓
User-facing app reads flags on server render → conditionally enables features

Part 5 — Implementation Plan (Phased Roadmap)

Execution strategy: Multi-agent parallel build. Each phase launches 2-3 simultaneous workstreams targeting independent systems, merged and tested at the end of each phase.
Phase 0 Database Foundation ~30 minutes

Objective: Get all tables live in Supabase. Everything else depends on this.

  • Run 00001_initial_schema.sql in Supabase SQL Editor (creates 10 tables, enums, functions, RLS, indexes, jurisdiction seeds)
  • Verify all 11 tables exist via Table Editor
  • Create Storage bucket: project-documents (private)
  • Set your profile's is_super_admin = true (after adding the column)
  • Run admin-specific migration (platform_config, feature_flags, announcements, admin_audit_log)
Phase 1 Core User Workflows Agent Workstream A + B + C in parallel

Agent A — Onboarding Flow

  • Signup → auto-create profile (trigger or post-signup API call)
  • First-login onboarding: create organization → set company name/type → invite members
  • Profile completion: avatar upload, notification preferences

Agent B — Project & Permit CRUD

  • Wire /app/projects to Supabase: list, create, update, archive
  • Wire /app/permits to Supabase: submit, track status, view history
  • Comment system: add, reply, resolve, mark category
  • Document upload: connect to Supabase Storage bucket

Agent C — Dashboard & Analytics (User-Facing)

  • Wire /app/dashboard to real data: active projects count, pending permits, upcoming deadlines
  • Activity feed from activity_log table
  • Wire /app/analytics: permit volume by jurisdiction, approval rate, avg review time
Phase 2 Admin Dashboard & Settings Agent Workstream D + E in parallel

Agent D — Admin Layout & Dashboard

  • Admin layout with sidebar (same Anthropic aesthetic: cream/forest/gold)
  • Super-admin middleware guard
  • Dashboard KPI cards: total users, total orgs, active projects, permit volume, lead count
  • Signup trend chart (daily/weekly signups over time)
  • Recent activity feed (platform-wide)

Agent E — Admin CRUD Pages

  • User management: search/filter, view detail, disable account
  • Org management: list with aggregate stats, drill into members
  • Lead pipeline: table view with status updates, inline notes, filter by intent/status
  • Feature flags UI: toggle on/off, target specific orgs
  • Platform config: key-value editor for site-wide settings
  • Announcements: create/edit/deactivate platform banners
  • Audit log: searchable table of admin actions
Phase 3 User Settings & Notifications Agent Workstream F

Agent F — Settings Backend (User-Facing)

  • Wire /app/settings: profile editing, password change, avatar upload
  • Organization settings: rename, update type, manage members, role assignment
  • Notification preferences: email on permit status change, comment reply, deadline due
  • Danger zone: delete account, leave organization
Phase 4 Polish & Production Hardening Final pass
  • Error boundaries on all data-fetching pages
  • Loading skeletons (use existing skeleton.tsx component)
  • Supabase Realtime subscriptions for live permit status updates
  • Email notifications via Supabase Edge Functions (permit approved, comment added)
  • Rate limiting on public API routes (/api/leads)
  • Custom domain setup (entitleflow.com or similar)
  • Supabase Pro upgrade (if needed — backups, larger storage, more auth users)

Part 6 — Trade-offs & Decisions

DecisionChosenAlternativeReasoning
Admin in same Next.js app /admin/* route group Separate admin app Simpler deployment, shared components, single Vercel project. Separate later if scale demands it.
Admin auth is_super_admin column Separate admin auth / RBAC system You're the only admin for now. Add RBAC later when you hire a team.
Feature flags storage Supabase table Vercel Edge Config / LaunchDarkly No additional service, queryable in SQL, auditable. Move to Edge Config for sub-ms reads at scale.
Admin API auth service_role key + user check Custom JWT middleware Bypasses RLS intentionally — admin needs to see all orgs. Guard is the is_super_admin check.
Analytics engine Supabase SQL aggregations PostHog / Mixpanel All data already in Supabase. SQL gives full flexibility. Add PostHog for user behavior tracking later.
Notifications Supabase Edge Functions Resend / SendGrid Edge Functions can call any email API. Start with Supabase's built-in email, upgrade to Resend for custom templates.

What to Revisit as the System Grows

TriggerAction
10+ admin usersImplement proper RBAC with roles table (viewer, editor, admin, super-admin)
1000+ concurrent usersAdd Redis caching layer for dashboard stats, move feature flags to Vercel Edge Config
100+ orgsAdd database connection pooling (Supabase Supavisor), consider read replicas
Complex email workflowsMove from Edge Functions to dedicated email service (Resend + react-email)
Compliance requirementsAdd data retention policies, GDPR deletion flows, SOC 2 audit trail hardening
